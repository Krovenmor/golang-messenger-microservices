# Signalline — фронтенд мессенджера

React + TypeScript + Vite + Tailwind клиент для API из ТЗ (Auth API, Message API, WebSocket).

## Структура проекта

```
src/
  api/          — HTTP-клиент (axios + авто-рефреш токена), обёртки над Auth/Message API, WebSocket-менеджер
  components/   — переиспользуемые UI-компоненты (Sidebar, ChatWindow, MessageBubble, модалки, поля форм)
  context/       — React Context для состояния авторизации/профиля
  pages/         — экраны: Login, Register, CreateProfile (создание профиля), Chats (основной экран)
  types/         — общие TypeScript-типы, отражающие контракты API
  utils/         — токены, генерация ключей (WebCrypto), цвет/инициалы по UUID, форматирование дат
```

## Как это работает

- **Auth**: `POST /auth/register`, `/auth/login` и `/auth/update`. `accessToken`/`refreshToken` лежат в `localStorage`; при 401 клиент сам обновляет токены через `/auth/update` и повторяет запрос (см. `src/api/client.ts`).
- **Профиль**: после регистрации пользователь создаёт публичный профиль (`POST /msg/profile`). Ключевая пара — ECDH P-256, генерируется в браузере через WebCrypto; приватный ключ шифруется AES-GCM на ключе, выведенном из пароля через PBKDF2 (`kdfSalt` + `keyNonce`) — на сервер уходит только шифртекст (`src/utils/crypto.ts`).
- **Сквозное шифрование сообщений**: на каждое сообщение генерируется одноразовый `MessageKey` (AES-256-GCM) и одноразовая эфемерная ECDH-пара. `MessageKey` запечатывается дважды — для собеседника (`receiverKey`) и для себя (`senderKey`, чтобы можно было перечитать свою историю), через `ECDH(ephemeral, targetPubKey) → HKDF-SHA256 → AES-KW`. Эфемерный публичный ключ приклеивается к каждому запечатанному блоку. Реализация: `src/utils/messageCrypto.ts`. При входе (или после потери ключа в памяти — например, после перезагрузки страницы) приватный ключ нужно заново расшифровать паролем на экране `/unlock` (`src/pages/UnlockProfile.tsx`, состояние — `src/api/cryptoStore.ts`); расшифровка текста сообщений — `src/utils/useDecryptedText.ts`.
- **Чаты**: список — `GET /msg/profile/chats/full`, история — `GET /msg/chat/{id}`, отправка/редактирование/удаление сообщений — соответствующие `POST/PUT/DELETE /msg/chat/{id}[/message/{id}]`.
- **Реалтайм**: `WS /api/ws?token=...` слушает `newChat`, `newMessage`, `messageRedacted`, `messageDeleted` — каждое событие тянет ровно одно точечное сообщение/чат (`src/api/chatStore.ts`), никогда не весь список заново. Соединение открывается только когда пользователь аутентифицирован **и** у него уже создан профиль (см. `AuthContext.tsx`) — до `/setup` сокет не трогается, и сам `SocketManager.connect()` защищён от повторного открытия (важно под React StrictMode, который в dev нарочно дважды прогоняет эффекты).
- **Статусы**: свой статус шлётся через сокет (`{"newStatus": N}`) — `Away` после минуты бездействия, `Typing` после 2 секунд непрерывного набора текста, откат на `Online` при активности/остановке набора (`src/utils/presence.ts`, тайминги настраиваются константами). Статус собеседника — `GET /api/status/{id}`, лёгкий поллинг раз в 20 секунд, пока открыт конкретный чат (push-события для статусов API не предусматривает).
- **История**: при открытии чата подгружаются последние 50 сообщений и кэшируются в `chatStore` на всю сессию — повторное открытие того же чата не бьёт по сети. Прокрутка вверх подгружает более старые сообщения через `from=<oldest message id>` постранично, пока бэкенд не вернёт пустую страницу.

## Дизайн

Тёмная тема с акцентным цветом сигнала (`#5EEAD4`) и монотонными техническими деталями (JetBrains Mono для времени/ID). Каждый собеседник получает стабильный «отпечаток»-цвет, выведенный из его UUID — им подсвечивается аватар и левая граница пузыря сообщения, без таблиц соответствий и лишней логики.

## Локальная разработка

```bash
npm install
cp .env.example .env   # при необходимости поменять VITE_API_URL / VITE_WS_URL
npm run dev
```

По умолчанию запросы идут на `/api` — в дев-режиме настройте прокси в `vite.config.ts` (`server.proxy`) на реальный бэкенд, либо задайте `VITE_API_URL` на полный адрес API.

## Сборка и запуск в Docker

Контейнер — чистый статик-сервер, никакого reverse-proxy внутри него нет: то, что стоит перед ним (гейтвей, балансировщик и т.д.), само отвечает за TLS и за маршрутизацию `/api`, `/api/ws`, `/static` куда нужно.

```bash
docker build -t signalline-web \
  --build-arg VITE_API_URL=/api \
  --build-arg VITE_STATIC_URL=/static \
  .

docker run -p 8080:80 signalline-web
```

`VITE_API_URL`/`VITE_WS_URL`/`VITE_STATIC_URL` — build-time аргументы, зашиваются в JS-бандл на этапе сборки и должны указывать туда, где API/WebSocket/Static Vault реально доступны из браузера (по умолчанию `/api` и `/static` — тот же origin, что и у фронта; `VITE_WS_URL` можно не задавать — адрес выведется из `location.host`). Если у API другой origin — задавайте здесь полный URL.

Двухэтапная сборка: Node собирает статику, nginx её отдаёт с fallback на `index.html` для клиентского роутинга.
